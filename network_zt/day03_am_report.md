## 문제 2-1 · 도메인 이름을 IP 주소로 — 두 DNS 서버에 묻기

### (가-1) 기본 DNS 서버로 example.com 조회

**명령어**
```bash
nslookup example.com
```

**실행 결과**
- DNS 서버: `kns.kornet.net`
- example.com IPv6: `2606:4700:10::ac42:93f3`
- example.com IPv4: `172.66.147.243`

### (가-2) Google DNS 서버로 example.com 조회

**명령어**
```bash
nslookup example.com 8.8.8.8
```

**실행 결과**
- DNS 서버: `dns.google` (`8.8.8.8`)
- example.com IPv6: `2606:4700:10::ac42:93f3`
- example.com IPv4: `172.66.147.243`

### (나) 위쪽 Address와 아래쪽 Addresses의 차이

위쪽 `Address`는 DNS 조회 요청을 처리하는 **DNS 서버의 IP 주소**이고, 아래쪽 `Addresses`는 조회 대상인 **example.com의 IP 주소 목록**이다.

첫 번째 조회에서는 통신사 DNS 서버인 `kns.kornet.net`을 사용했고, 두 번째 조회에서는 Google DNS 서버인 `8.8.8.8`을 사용했다.

두 화면에서 DNS 서버는 달라졌지만, 조회된 example.com의 IPv4 주소는 `172.66.147.243`으로 같았다.

즉, **위쪽 주소는 질문을 받는 DNS 서버의 주소이고, 아래쪽 주소는 DNS 서버가 찾아준 웹사이트의 주소**이다.

단, DNS 서버가 다르거나 조회 시점이 달라지면 반환되는 IP 주소도 달라질 수 있다.

### (다-1) 회사 PC가 외부 DNS 서버에 직접 질의하면 관제 담당자가 확인해야 하는 이유

**① 회사 DNS 서버가 하는 일**

회사 DNS 서버는 도메인 이름을 IP 주소로 변환하는 역할을 한다. 또한 회사의 보안 정책에 따라 악성 도메인 접속을 차단하고, DNS 조회 기록을 남겨 보안 관제에 활용할 수 있다. 회사 내부 시스템의 도메인 주소를 관리하기도 한다.

**② 외부 DNS 서버에 직접 질의할 때 발생하는 문제**

회사 PC가 `8.8.8.8`과 같은 외부 DNS 서버에 직접 질의하면 회사 DNS 서버를 거치지 않는다.

따라서 회사 DNS 서버에 적용된 도메인 차단 정책이 우회되거나, 해당 DNS 서버의 조회 기록에 남지 않아 의심스러운 접속을 탐지하기 어려워질 수 있다.

외부 DNS 사용 자체가 악성 행위는 아니지만, **보안 정책 우회나 관제 사각지대가 발생할 가능성**이 있으므로 확인이 필요하다.

### (다-2) PC의 DNS 서버가 낯선 주소로 변경되면 발생할 수 있는 일

**① 낯선 DNS 서버가 줄 수 있는 답**

악의적인 DNS 서버라면 정상적인 도메인 이름을 조회하더라도 실제 서버의 IP 주소가 아닌 공격자가 지정한 가짜 서버의 IP 주소를 반환할 수 있다.

**② 그 답 때문에 발생할 수 있는 일**

PC는 DNS 서버가 알려준 IP 주소로 접속을 시도하므로, 정상적인 사이트 대신 공격자가 만든 가짜 사이트로 연결될 수 있다.

사용자가 가짜 로그인 페이지에 아이디와 비밀번호를 입력하면 계정 정보가 유출될 위험이 있다.

이러한 공격은 DNS 하이재킹(DNS Hijacking)과 관련이 있다. 다만 HTTPS 인증서 검증이 정상적으로 이루어지면 가짜 사이트 접속 시 보안 경고가 나타나거나 연결이 차단될 수 있다.

## 문제 2-2 · URL에서 이름을 꺼내 묻기 — 없는 이름이면

### (가-1) day03_2-2_url_example.py 실행 결과

```text
['https:', '', 'example.com', 'news', 'today']
example.com → 104.20.23.154
```

URL을 `/` 기준으로 나눈 뒤 도메인 이름인 `example.com`을 추출하고, `socket.gethostbyname()`으로 IPv4 주소를 조회한 결과이다.

### (가-2) day03_2-2_url_nowhere.py 실행 결과

**Python 에러**
```text
socket.gaierror: [Errno 11001] getaddrinfo failed
```

**nslookup 결과**
```text
kns.kornet.net이(가) abc.nowhere-not-exist.com을(를) 찾을 수 없습니다. Non-existent domain
```

### (나-1) parts[2]에 도메인 이름이 저장되는 이유

`split("/")`은 `/`를 구분자로 사용하여 URL 문자열을 나눈다.

```python
url = "https://example.com/news/today"
parts = url.split("/")
```

**리스트의 각 위치**

| 인덱스 | 저장된 값 |
|---|---|
| `parts[0]` | `'https:'` |
| `parts[1]` | `''` (빈 문자열) |
| `parts[2]` | `'example.com'` |
| `parts[3]` | `'news'` |
| `parts[4]` | `'today'` |

`https://`에서 `/`가 두 번 연속 나오기 때문에 두 `/` 사이에 빈 문자열 `''`이 생성된다.

따라서 도메인 이름인 `example.com`이 `parts[2]`에 저장된다.

### (나-2) 두 번째 파일이 마지막 줄에서 에러가 발생한 이유

**① gethostbyname()이 DNS 서버에 물어본 것**

`socket.gethostbyname()`은 `abc.nowhere-not-exist.com`이라는 도메인 이름에 해당하는 IPv4 주소를 조회하려고 했다.

**② DNS 서버의 응답**

`nslookup` 결과에서 `Non-existent domain`이 나타났다. 이는 DNS 서버가 해당 도메인 이름이 존재하지 않는다고 응답했다는 의미이며, `NXDOMAIN`이라고 한다.

**③ 에러가 발생한 이유**

해당 도메인의 IPv4 주소를 얻지 못했기 때문에 `gethostbyname()`은 IP 주소 대신 `socket.gaierror` 예외를 발생시켰다.

코드에 `try-except` 예외 처리가 없어 프로그램이 에러와 함께 종료되었다.

### (다) NXDOMAIN이 나왔다고 인터넷이 끊긴 것은 아닌 이유

`NXDOMAIN`은 인터넷 연결이 끊겼다는 의미가 아니라, **DNS 서버가 조회 요청에 응답했지만 해당 도메인 이름이 존재하지 않는다고 알려준 것**이다.

이번 실습에서는 `nslookup`이 DNS 서버인 `kns.kornet.net`으로부터 `Non-existent domain`이라는 응답을 받았으므로 DNS 조회 요청과 응답이 이루어졌음을 알 수 있다.

반면 인터넷 연결이 끊겼거나 DNS 서버에 접근할 수 없다면 DNS 요청에 대한 응답을 받지 못해 시간 초과(`timeout`) 또는 서버 연결 실패와 같은 오류가 발생할 수 있다.

따라서 `NXDOMAIN`은 인터넷 전체의 연결 상태가 아니라 **조회한 도메인 이름의 존재 여부에 관한 DNS 응답**이다.

## 이 교시에 새로 안 것

DNS 서버는 도메인 이름을 IP 주소로 변환해 주지만, 잘못된 IP 주소를 알려주면 정상적인 사이트 대신 다른 사이트로 연결될 수도 있다는 것을 알게 되었다.

평소에는 DNS 서버가 어떤 주소를 알려주는지 신경 쓰지 않았는데, DNS 설정이 단순한 인터넷 연결뿐 아니라 보안에도 영향을 줄 수 있다는 점이 기억에 남았다.

### 문제 3-2 · 권한 있는 네임서버에게 직접 묻기

**(가-1) `nslookup example.com`으로 리졸버에 물은 결과**

- 권한 없는 응답: 있음
- IPv4 주소: `172.66.147.243`

**(가-2) 권한 있는 네임서버에 직접 물은 결과**

- 권한 없는 응답: 없음 (정상적인 권한 있는 응답을 받은 경우)
- IPv4 주소: 직접 조회한 결과를 확인해야 함

**(나-1) 두 화면에서 `권한 없는 응답:` 줄이 한쪽에만 나온 이유**

첫 번째 화면은 내 PC에 설정된 재귀 리졸버가 응답한 결과이다. 재귀 리졸버는 캐시에 저장된 정보를 사용하거나 권한 있는 네임서버에 질의하여 얻은 결과를 전달하므로 `권한 없는 응답`이라고 표시된다.

반면 두 번째 화면은 `example.com`의 권한 있는 네임서버에 직접 질의한 결과이다. 해당 도메인의 DNS 정보를 관리하는 서버가 권한 있는 응답을 제공했기 때문에 `권한 없는 응답`이라는 문구가 나타나지 않는다.

**(나-2) 권한 없는 응답은 정말 틀린 답일까?**

권한 없는 응답이라고 해서 잘못된 정보라는 뜻은 아니다.

재귀 리졸버는 권한 있는 네임서버에서 얻은 정보를 캐시에 저장하거나 전달하기 때문에 정상적인 IP 주소를 알려줄 수 있다.

두 조회 결과의 IPv4 주소가 같다면 같은 주소를 반환한 것이고, 다르더라도 캐시 갱신 시점이나 DNS 응답 정책 등에 따라 정상적으로 차이가 발생할 수 있다.

**(다) 리졸버의 응답이 이상할 때 권한 있는 네임서버에 직접 물어보면 알 수 있는 것**

두 서버가 같은 IP 주소를 반환한다면 리졸버가 권한 있는 네임서버의 정보와 일치하는 결과를 제공하고 있음을 확인할 수 있다.

반대로 IP 주소가 다르다면 DNS 캐시가 오래되었거나 서버별 응답 정책이 다를 가능성이 있다. 경우에 따라 DNS 설정 오류나 응답 변조도 의심할 수 있다.

따라서 권한 있는 네임서버에 직접 질의하면 **재귀 리졸버의 응답과 비교하여 DNS 조회 결과의 차이를 분석하는 데 도움**이 된다.

## 문제 4-1 · 메일 서버와 별칭 — MX · CNAME

### (가-1) `nslookup -type=mx google.com`

**답:**

- 메일 서버 이름: `smtp.google.com`
- MX 우선순위: `10`

### (가-2) `nslookup www.naver.com`

**답:**

- 별칭(Aliases): `www.naver.com`
- 정식 이름(Name): `www.naver.com.nheos.com`

### (나-1) MX 레코드는 왜 IP가 아니라 서버 이름으로 답할까요? 그 서버의 IP는 어떻게 알아낼까요?

**답:**

MX 레코드에 IP 주소 대신 서버 이름을 저장하면 메일 서버의 IP 주소가 변경되어도 MX 레코드를 수정할 필요가 없다는 장점이 있다.

메일 서버의 IP 주소를 알아내려면 MX 레코드에서 확인한 서버 이름을 **A 레코드(IPv4) 또는 AAAA 레코드(IPv6)**로 다시 조회하면 된다.

예를 들어 `google.com`의 MX 레코드가 `smtp.google.com`을 가리킨다면, `smtp.google.com`의 A 레코드를 조회해 IP 주소를 확인할 수 있다.

### (나-2) `www.naver.com`은 왜 다른 이름(정식 이름)을 가리키고 있을까요?

**답:**

CDN(Content Delivery Network)은 여러 지역에 서버를 두고 사용자에게 가까운 서버에서 웹 콘텐츠를 빠르게 제공하는 서비스이다.

네이버처럼 이용자가 많은 사이트는 CNAME을 이용해 사용자에게 익숙한 `www.naver.com`을 CDN이 관리하는 도메인 이름에 연결할 수 있다.

이렇게 하면 **CDN 서버의 IP 주소가 변경되어도 `www.naver.com`의 CNAME 설정을 바꿀 필요가 없고**, 사용자도 기존 주소로 계속 접속할 수 있다. 또한 CDN을 통해 접속 속도를 높이고 서버의 부담을 분산할 수 있다.

다만 실제 `www.naver.com.nheos.com`이 CDN용 이름인지는 DNS 조회 결과만으로 확정할 수 없다.

### (다) 🔍 의심스러운 메일을 받았을 때, 보낸 쪽 도메인의 MX 레코드를 확인하면 무엇을 알 수 있을까요?

**답:**

정상적인 회사 도메인은 메일을 받기 위해 보통 MX 레코드에 회사가 직접 운영하거나 Google, Microsoft 같은 외부 메일 서비스의 서버를 등록해 둔다.

의심스러운 메일을 받았을 때 보낸 쪽 도메인의 MX 레코드를 확인하면 **해당 도메인이 어떤 메일 서버를 통해 이메일을 수신하도록 설정되어 있는지** 알 수 있다.

MX 레코드가 없거나 낯선 서버로 설정되어 있다면 메일 서비스 설정 오류, 가짜 도메인 또는 공격자가 관리하는 도메인일 가능성을 의심할 수 있다.

다만 **MX 레코드가 없거나 낯설다고 해서 반드시 악성 메일인 것은 아니다.** 메일 발송만 하는 도메인에는 MX 레코드가 없을 수도 있으며, MX 레코드만으로 발신자의 진위를 판단할 수는 없다. 정확한 확인을 위해서는 SPF, DKIM, DMARC 같은 이메일 인증 정보도 함께 살펴봐야 한다.


### (나) 첫 파일과 두 번째 파일에서 100초 줄의 결과가 다릅니다. 왜 그럴까요?

**답:**

첫 번째 파일은 TTL이 300초이고 저장 시각이 0초이므로 **만료 시각은 300초**이다. 100초는 만료 시각인 300초보다 작기 때문에 `캐시의 답을 쓴다`가 출력된다.

두 번째 파일은 TTL이 60초이고 저장 시각이 0초이므로 **만료 시각은 60초**이다. 100초는 만료 시각인 60초보다 크기 때문에 `DNS 서버에 새로 묻는다`가 출력된다.

즉, **TTL이 짧을수록 캐시가 더 빨리 만료되기 때문에** 두 파일의 100초 결과가 다르게 나타난다.

### (다-1) 🔍 사이트가 서버 IP를 바꿨는데도, 한동안은 옛 IP로 접속되는 사람이 있습니다. 왜 그럴까요?

**답:**

DNS 캐시에는 도메인 이름과 연결된 IP 주소 등의 정보가 일정 시간 저장된다.

웹사이트의 서버 IP 주소가 변경되더라도 **TTL이 지나기 전에는 기존 캐시에 저장된 IP 주소를 계속 사용할 수 있다.**

따라서 어떤 사용자는 새로운 IP 주소로 접속하지만, 아직 캐시가 만료되지 않은 사용자는 옛 IP 주소로 접속할 수 있다.

TTL이 만료된 후 DNS 정보를 다시 조회하면 변경된 IP 주소를 받아올 수 있다.

### (다-2) 어떤 PC가 계속 이상한 주소로 접속된다면, 관제 담당자는 왜 `ipconfig /flushdns`부터 해 볼까요?

**답:**

PC의 DNS 캐시에는 도메인에 연결된 **오래된 IP 주소나 잘못된 DNS 조회 결과**가 남아 있을 수 있다. 이 때문에 서버의 IP 주소가 변경되었거나 DNS 정보가 수정되었어도 PC가 계속 이상한 주소로 접속할 수 있다.

관제 담당자는 `ipconfig /flushdns` 명령어로 PC에 저장된 DNS 캐시를 삭제해 볼 수 있다.

캐시를 비운 뒤 해당 도메인에 다시 접속하면 PC는 **설정된 DNS 서버(재귀 리졸버)에 IP 주소를 다시 요청**한다.

이를 통해 PC의 오래된 DNS 캐시가 문제의 원인인지 확인할 수 있다. 다만 DNS 서버 자체에 잘못된 정보가 남아 있다면 캐시를 비워도 문제가 해결되지 않을 수 있다.
