### 문제 2-4. 두 가지 실패를 구별하기

#### ① DNS 이름 해석 실패

**실행 명령어**

```bash
ping abc.nowhere-not-exist
```

**실행 결과**

```text
Ping 요청에서 abc.nowhere-not-exist 호스트를 찾을 수 없습니다.
이름을 확인하고 다시 시도하십시오.
```

**분석:** 도메인 이름을 IP 주소로 변환하지 못해 ICMP Echo Request를 보내기 전에 실패한 경우.

#### ② IP 통신 응답 실패

**실행 명령어**

```bash
ping 192.0.2.1
```

**실행 결과**

```text
Ping 192.0.2.1 32바이트 데이터 사용:
요청 시간이 만료되었습니다.
요청 시간이 만료되었습니다.
요청 시간이 만료되었습니다.
```

**분석:** IP 주소로 ping을 시도했지만 제한 시간 내에 ICMP Echo Reply를 받지 못한 경우. 패킷 손실, 경로 문제, ICMP 차단 등이 원인일 수 있음.

> **핵심 차이:** ①은 DNS 이름 해석 실패, ②는 ICMP 응답을 받지 못한 경우.

### 찾아본 것

- 2.1 표에서 찾아 쓴 TTL 의 뜻과 라우터를 지날 때 바뀌는 방식: 
    ### TTL(Time To Live)의 의미와 동작 방식

    #### ① TTL의 의미

    TTL은 IP 패킷이 네트워크에서 무한히 순환하지 않도록 제한하는 값이다.

    #### ② TTL의 동작 방식

    | 구분 | 설명 |
    |---|---|
    | 초기 TTL | 출발지에서 설정하는 값 (예: 64, 128) |
    | TTL 감소 | 라우터를 통과할 때마다 1씩 감소 |
    | TTL 만료 | 라우터에서 TTL이 0이 되면 패킷 폐기 |
    | 목적 | 라우팅 루프 발생 시 패킷이 무한히 순환하는 현상 방지 |

    #### ③ TTL 계산 공식

    **남은 TTL = 초기 TTL − 거친 라우터 수(홉 수)**

    **계산 예시**

    - 초기 TTL: `64`
    - 거친 라우터 수: `5`
    - 남은 TTL: `64 - 5 = 59`

    > **핵심 정리:** TTL은 라우터를 통과할 때마다 1씩 감소하며, TTL이 만료되면 패킷이 폐기된다.
    > &nbsp;

        계산 공식
        남은 TTL = 초기 TTL − 거친 라우터 수(홉 수)

### 문제 3-3 · 게이트웨이까지 `ping`

> **① 응답 시간 비교**
>
> | 대상 | 최소 RTT | 최대 RTT | 평균 RTT |
> |---|---:|---:|---:|
> | 기본 게이트웨이 (`192.168.1.1`) | 0ms | 1ms | 0ms |

#### ② 게이트웨이까지의 응답 시간이 더 짧은 이유

- **기본 게이트웨이:** 내 PC와 같은 로컬 네트워크에 있어 비교적 짧은 경로로 통신할 수 있음

> **핵심 정리:** 기본 게이트웨이는 로컬 네트워크에 있으므로 외부 서버보다 일반적으로 RTT가 짧다. 단, 실제 응답 시간은 네트워크 혼잡과 장비의 ICMP 처리 방식 등에 따라서도 달라질 수 있다.

### 문제 4-1 · 직접 실행해 보기

> **① 실행 코드**
>
> ```python
> PORTS = {80: "HTTP", 443: "HTTPS", 53: "DNS"}

> ```
>
> **② 실행 결과**

> ```text

> **③ `3389`는 사전에 없는데도 오류가 발생하지 않은 이유**
>

>
> - `PORTS[443]` → 키가 존재하므로 `"HTTPS"` 반환
> - `PORTS.get(3389, "모름")` → 키가 없으므로 `"모름"` 반환
>
> **핵심 정리:** `get()`은 존재하지 않는 키를 조회해도 기본값을 지정했다면 `KeyError`가 발생하지 않는다.

### 문제 4-4 · 내 PC의 LISTENING 포트 찾기

> **① 실행 명령어**
>
> ```bash
> netstat -ano | grep LISTENING
> ```
>
> **② 실행 결과**
>
> ```text
> TCP [::]:49664    [::]:0  LISTENING  1504
> TCP [::]:49665    [::]:0  LISTENING  1332
> TCP [::]:49666    [::]:0  LISTENING  1248
> TCP [::]:49667    [::]:0  LISTENING  2932

> TCP [::1]:42050   [::]:0  LISTENING  23256
> TCP [::1]:49669   [::]:0  LISTENING  4504
> ```
>
> **③ 선택한 포트의 프로세스 확인**
>
> ```bash
> tasklist | grep 23256
> ```
>
> **실행 결과**
>
> ```text
> OneDrive.Sync.Service.exe  23256  Console  15  66,688 K
> ```
>
> **④ 확인한 정보**
>
> | 항목 | 값 |
> |---|---|
> | 로컬 주소 | `[::1]` |
> | LISTENING 포트 | `42050` |
> | PID | `23256` |
> | 프로그램 이름 | `OneDrive.Sync.Service.exe` |
> | 연결 상태 | `LISTENING` |
>
> `[::1]`은 IPv6 루프백 주소로, 해당 포트는 로컬 PC 내부의 연결을 기다리고 있다.
>
> **⑤ LISTENING과 ESTABLISHED의 차이**
>
> | 구분 | LISTENING | ESTABLISHED |
> |---|---|---|
> | 의미 | 새로운 TCP 연결 요청 대기 | TCP 연결 성립 |
> | 상태 | 연결을 받아들일 준비 | 데이터 송수신 가능 |
> | 실습 예시 | `[::1]:42050` | `192.168.100.174:50082` → `52.98.51.162:443` |
>
> **핵심 정리:** `LISTENING`은 연결 요청을 기다리는 상태이고, `ESTABLISHED`는 TCP 연결이 성립되어 데이터를 주고받을 수 있는 상태이다.

### 문제 4-5 · 증상으로 층 좁히기

- 증상 ① · ② · ③ 에서 의심되는 층:
    | 증상 | 의심되는 계층 | 판단 근거 |
    |---|---|---|
    | ① IP로 ping은 성공하지만 도메인으로는 실패 | 7계층 응용 계층 | IP 통신은 가능하지만 도메인 이름을 IP로 변환하는 DNS 조회에 문제가 있을 가능성이 높음 |
    | ② 기본 게이트웨이로 ping을 보내도 응답 없음 | 2계층 데이터 링크 / 3계층 네트워크 계층 | 게이트웨이와 통신하지 못하므로 ARP, 네트워크 설정, 연결 상태 등을 의심할 수 있음 |
    | ③ ping은 성공하지만 특정 웹사이트만 접속 불가 | 4계층 전송 계층 / 7계층 응용 계층 | IP 통신은 가능하지만 웹서비스의 포트 연결 또는 HTTP/HTTPS 처리에 문제가 있을 수 있음 |


- **증상마다 그렇게 판단한 근거는 무엇인가요?**

  - **① DNS 문제 의심 — 7계층**

    - `ping 8.8.8.8` → 성공
    - `ping google.com` → 호스트 이름 조회 실패
    - DNS 이름 해석 문제를 우선 의심할 수 있음.

  - **② 게이트웨이 통신 문제 의심 — 2~3계층**

    - 기본 게이트웨이에 `ping`을 보냈지만 응답 없음.
    - ARP, IP 설정 및 네트워크 연결 상태 점검 필요.
    - ICMP 차단 가능성이 있으므로 장애 확정은 불가능.

  - **③ 웹서비스 문제 의심 — 4~7계층**

    - `ping` 성공 → ICMP를 이용한 IP 통신 가능
    - 웹사이트 접속 실패 → TCP 연결, TLS, HTTP/HTTPS 문제 가능성
    - 방화벽이나 웹서버 장애도 점검 필요.


### 찾아본 것  
- **4.1 표에서 찾아 쓴 3389의 위험과 445를 이용해 퍼진 랜섬웨어**

  - **3389번 포트 — RDP(Remote Desktop Protocol)**

    3389번 포트는 Windows 원격 데스크톱(RDP)에 사용되는 기본 포트이다. 다른 컴퓨터에서 원격으로 접속하여 화면을 확인하고 마우스와 키보드를 조작할 수 있다.

    **① 인터넷에 노출되었을 때의 위험**

    | 위험 | 설명 |
    |---|---|
    | 무차별 대입 공격 | 비밀번호를 반복적으로 입력하여 로그인을 시도 |
    | 계정 탈취 | 유출된 계정 정보를 이용한 무단 원격 접속 |
    | 취약점 악용 | RDP 및 운영체제의 보안 취약점을 이용한 공격 |
    | 랜섬웨어 감염 | 원격 접속에 성공한 공격자가 파일 암호화 등 추가 공격 수행 |
    | 내부망 침투 | 침해된 PC를 통해 내부 네트워크의 다른 시스템으로 공격 확대 |

    **② 보안 대책**

    - RDP 3389번 포트를 인터넷에 직접 노출하지 않기
    - VPN 또는 원격 데스크톱 게이트웨이를 통한 접근
    - 다중 인증(MFA) 및 강력한 비밀번호 적용
    - 운영체제와 RDP 관련 보안 업데이트 유지
    - 방화벽을 이용한 접근 IP 제한

    **핵심 정리:** 3389번 포트 자체가 위험한 것은 아니지만, 인증과 접근 통제가 부족한 상태로 인터넷에 노출되면 계정 탈취, 랜섬웨어 감염, 내부망 침투 등의 보안 위협이 발생할 수 있다.


    
  - **445번 포트 — SMB(Server Message Block)**

    445번 포트는 Windows에서 파일 및 프린터 공유에 사용되는 SMB 프로토콜의 기본 포트이다. 같은 네트워크의 컴퓨터끼리 파일이나 프린터 등의 자원을 공유할 수 있도록 지원한다.

    **① SMB 포트를 이용해 확산된 랜섬웨어**

    대표적인 사례는 **2017년에 전 세계적으로 확산된 워너크라이(WannaCry) 랜섬웨어**이다.

    워너크라이는 Windows SMBv1의 취약점인 **MS17-010**을 악용하는 EternalBlue 공격 기법을 이용해 확산되었다.

    감염된 컴퓨터에서 다른 컴퓨터의 445번 포트로 접근하여 취약점을 악용했고, 사용자 개입 없이 네트워크를 통해 자동으로 전파될 수 있었다.

    **② 인터넷에 노출되었을 때의 위험**

    | 위험 | 설명 |
    |---|---|
    | 랜섬웨어 확산 | WannaCry처럼 SMB 취약점을 악용하여 다른 컴퓨터로 감염 확산 |
    | 취약점 악용 | 보안 패치가 적용되지 않은 SMB 서비스의 취약점을 이용한 공격 |
    | 무단 파일 접근 | 공유 폴더의 접근 권한이 잘못 설정된 경우 중요 파일 유출 가능 |
    | 내부망 침투 | 침해된 컴퓨터를 통해 같은 네트워크의 다른 시스템으로 공격 확대 |

    **③ 보안 대책**

    - SMB 445번 포트를 인터넷에 직접 노출하지 않기
    - 사용하지 않는 SMBv1 프로토콜 비활성화
    - Windows 보안 업데이트 및 MS17-010 패치 적용
    - 방화벽으로 SMB 접근 가능한 IP와 네트워크 제한
    - 공유 폴더에 최소 권한 원칙 적용
    - 사용하지 않는 파일 및 프린터 공유 기능 비활성화

    **핵심 정리:** 445번 포트는 Windows의 파일 및 프린터 공유에 사용되지만, SMB 취약점이나 잘못된 접근 권한 설정이 존재하면 랜섬웨어 확산과 무단 파일 접근 등의 보안 위협이 발생할 수 있다.

### 문제 5-3 · 세 번의 순서 맞히기

- **① TCP 3-Way Handshake — 연결 수립**

  ```text
  내 PC                            서버
    │                               │
    │ ────── ① SYN ───────────────▶ │  연결 요청
    │ ◀───── ② SYN + ACK ───────── │  요청 확인 및 응답
    │ ────── ③ ACK ───────────────▶ │  응답 확인
    │                               │
    │        ESTABLISHED            │
    │       데이터 송수신 가능         │
  ```

- **② TCP 4-Way Handshake — 연결 종료**

  ```text
  내 PC                            서버
    │                               │
    │ ────── ① FIN ───────────────▶ │  종료 요청
    │ ◀───── ② ACK ─────────────── │  종료 요청 확인
    │ ◀───── ③ FIN ─────────────── │  서버도 종료 요청
    │ ────── ④ ACK ───────────────▶ │  종료 요청 확인
    │                               │
    │       연결 종료 절차 진행        │
  ```

- **③ 연결을 맺을 때는 세 번인데, 끝낼 때는 왜 네 번인가요?**

  연결할 때는 서버가 SYN과 ACK를 함께 전송할 수 있어 3번이면 되지만, 종료할 때는 상대방에게 아직 보낼 데이터가 남아 있을 수 있어 ACK와 FIN을 따로 전송하므로 일반적으로 4번의 과정이 필요하다.

### 이 교시에 새로 안 것

#### 헤더(Header)와 페이로드(Payload)

- **헤더(Header):** 데이터를 어디로, 어떻게 전달할지 알려주는 제어 정보
- **페이로드(Payload):** 실제로 전달하려는 데이터

**① 기본 구조**

```text
[ 헤더(Header) | 페이로드(Payload) ]
```

**② 계층별 데이터 구조**

```text
4계층  [ TCP 헤더 | 데이터 ]
3계층  [ IP 헤더 | TCP 헤더 | 데이터 ]
2계층  [ 이더넷 헤더 | IP 헤더 | TCP 헤더 | 데이터 | FCS ]
```

**③ 계층별 주요 정보**

| 구분 | 주요 정보 |
|---|---|
| 이더넷 헤더 (2계층) | 출발지·목적지 MAC 주소 |
| IP 헤더 (3계층) | 출발지·목적지 IP 주소, TTL |
| TCP 헤더 (4계층) | 출발지·목적지 포트, TCP 플래그 |
| 페이로드 | 실제 전송할 데이터 |

**핵심 정리:** 데이터를 전송할 때 계층마다 헤더가 추가되는 과정을 **캡슐화(Encapsulation)**라고 하며, 수신할 때 헤더를 역순으로 해석하고 제거하는 과정을 **역캡슐화(Decapsulation)**라고 한다.
