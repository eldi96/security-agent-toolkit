  - 답: 처리 뒤 티켓은 1건, 담당자 알림은 1건이다. 분류됨으로 남은 알림은 INC-005이며, 승인 권한이 없는 사람의 결정이라 실행되지 않았다.

```

INC-002 seoyeon · PB-002 · 플레이북 승인 값이 담당자 승인 필요
```

## 6교시 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으고, 오늘 만든 하루 흐름 전체 읽기

### 문제 6-1 · 연결 오류가 나면 최대 3번 시도하고, 실패한 건을 목록으로 모으기

- (가) 실행한 출력 전체를 붙여 넣고, 단계 3 에서 `일부 실패` · `승인 대기` · `오탐 종료`(오탐: 위험하지 않은데 위험하다고 잘못 알린 경우) 인 알림의 번호를 각각 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② `일부 실패` 인 알림 번호 ③ `승인 대기` 인 알림 번호 ④ `오탐 종료` 인 알림 번호
  - 답: 단계 3에서 일부 실패는 INC-001, 승인 대기는 INC-002 · INC-003 · INC-005, 오탐 종료는 INC-004이다.

```text
--- 단계 1: 일시 장애 — 티켓 서비스가 2번 실패한 뒤 복구
티켓 TCK-1 생성 (시도 3회)
만든 티켓: 1 건
--- 단계 2: 서비스 중단 — 티켓 서비스가 계속 실패
실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
만든 티켓: 0 건
--- 단계 3: 하루 흐름 — 티켓 서비스가 계속 실패하는 상황
INC-001 dami -> 일부 실패 (상태: 분류됨)
INC-002 seoyeon -> 승인 대기 (상태: 분류됨)
INC-003 gaeun -> 승인 대기 (상태: 분류됨)
INC-004 jiwoo -> 오탐 종료 (상태: 종료)
INC-005 198.51.100.90 -> 승인 대기 (상태: 분류됨)
--- 단계 4: 담당자 결정 처리
INC-002 seoyeon -> 실행 완료 (상태: 조치됨)
INC-003 gaeun -> 거절 처리 (상태: 종료)
INC-005 198.51.100.90 -> 권한 없음 (상태: 분류됨)
--- 단계 5: 하루가 끝난 뒤 모의 시스템 상태
잠긴 계정: ['dami']
차단한 IP: []
티켓: 1 건 · 담당자 알림: 1 건
--- 단계 6: 담당자 확인이 필요한 건
INC-001 티켓 생성 : 실패: 연결 실패: 티켓 생성 서비스가 응답하지 않음 (3회 모두 실패)
INC-005 승인 대기 : 플레이북 승인 값이 담당자 승인 필요
```

- (나) 🔍 단계 1 과 2 는 같은 `run_with_retry` 인데 결과가 다릅니다. 두 단계의 `fail_plan` 값을 근거로 이유를 적어 주세요. 그리고 최대 횟수가 없으면 서비스가 계속 멈춰 있을 때 어떤 문제가 생기는지도 적어 주세요.
  - 쓸 내용: ① 단계 1 과 2 의 `fail_plan` 값 ② 결과가 달라진 이유 ③ 최대 시도 횟수가 없을 때의 문제
  - 답: 단계 1의 fail_plan은 {"INC-001|티켓 생성": 2}여서 두 번 실패한 뒤 세 번째 시도에 성공한다. 단계 2는 같은 항목의 값이 99라 최대 3번을 시도해도 계속 실패한다. 최대 횟수가 없으면 복구되지 않는 서비스를 계속 호출하며 다음 처리가 끝없이 지연될 수 있다.

- (다) 🔍 단계 3 에서 INC-001 은 계정은 잠겼는데 상태가 `조치됨` 이 아닙니다. 그 이유를 적어 주세요. 또 단계 6 의 출력이 담당자에게 무엇을 알려 주는지 적어 주세요. 마지막으로, 같은 `state` 로 다시 처리해도 `dami` 가 두 번 잠기지 않는 이유를 오전 4교시에서 만든 장치와 연결해 적어 주세요.
  - 쓸 내용: ① INC-001 이 `조치됨` 이 아닌 이유 ② 단계 6 이 담당자에게 알려 주는 것 ③ 다시 실행해도 `dami` 가 두 번 잠기지 않는 이유
  - 답: INC-001은 계정 잠금에는 성공했지만 티켓 생성이 3번 모두 실패해 일부 실패로 처리되고, 상태는 분류됨으로 남는다. 모든 조치가 성공해야 조치됨으로 바뀐다. 단계 6은 담당자에게 INC-001의 티켓 생성 실패와 INC-005의 미처리 승인 대기를 알려 준다. 같은 state로 다시 처리하면 오전 4교시의 safe_run_action이 locked_users에 dami가 이미 있는지 확인해 중복 잠금을 막는다. INC-001은 완료 상태가 아니므로, 이 경우에는 상태 검사보다 조치별 중복 확인이 핵심이다.
