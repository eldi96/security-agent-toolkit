# 3과목 총정리 (전병현 · 2026-11-02(월))

## 상황 1 · 새 직원이 들어옴 (본보기)

- 원인: 데이터 문제입니다. hana 가 입사했는데 `users.json` 에 hana 가 아직 없습니다. 시스템은 사용자 파일에 없는 사람의 요청을 모두 「등록되지 않은 사용자」로 거부합니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: 새로 넣습니다. hana 를 `"hana": {"role": "sales", "employed": true}` 로 `users.json` 에 적습니다. `role` 은 hana 가 맡을 일에 맞는 역할로 정합니다.
- 고친 뒤 확인: hana 의 요청을 다시 판정해서 「등록되지 않은 사용자」가 사라지는지 봅니다.

## 상황 2 · 퇴사자 계정으로 요청이 계속 들어옴 (본보기)

- 원인: 데이터가 정리되지 않았습니다. dami 는 퇴사했는데 dami 의 항목이 `users.json` 에 그대로 남아 있어서 같은 시도가 계속 들어옵니다. `employed` 가 `false` 이면 요청은 거부되지만, 남은 항목 때문에 퇴사자 계정 점검에는 계속 걸립니다.
- 고칠 파일: `config/users.json`
- 어떻게 고치나요: dami 의 `"employed"` 가 `true` 로 남아 있다면 먼저 `false` 로 바꿉니다. 이미 `false` 이면 그대로 두고, 계정과 권한을 정리한 후 dami 의 항목을 `users.json` 에서 삭제합니다.
- 고친 뒤 확인: 같은 요청이 「등록되지 않은 사용자」로 거부되고, 퇴사자 계정 점검이 통과로 바뀌는지 봅니다.
- 더 써 보고 싶은 것(선택): `check_permission` 이 퇴사 여부를 역할 확인보다 먼저 보는 이유는 퇴사한 사용자는 역할이나 권한이 남아 있더라도 접근하면 안 되기 때문입니다. 먼저 퇴사 여부를 확인하면 불필요한 권한 검사를 진행하지 않고 바로 거부할 수 있습니다.

## 상황 3 · 다른 팀 업무를 잠시 지원함

- 원인: 기존 역할에는 다른 팀의 업무 권한이 없기 때문입니다. 하지만 잠시 지원하는 업무를 위해 역할 자체를 변경하면 필요하지 않은 권한까지 생길 수 있습니다.
- 고칠 파일: `config/exceptions.json`
- 어떻게 고치나요: 먼저 지원할 업무와 필요한 권한을 확인합니다. 승인받은 뒤 `exceptions.json`에 사용자, 권한, 예외 번호, 만료 시각을 등록합니다. 기존 역할은 그대로 유지하고 필요한 권한만 임시로 추가합니다.
- 고친 뒤 확인: `policy.py`의 `evaluate_access()`로 요청을 판정합니다. 예외가 유효한 기간에는 「예외 N번」으로 허용되고, 만료 시각이 지나면 다시 「권한 없음」으로 거부되는지 확인합니다.
- 더 써 보고 싶은 것(선택): 임시 업무 지원에 역할을 변경하는 것보다 예외 권한을 사용하는 이유는 필요한 권한만 일정 기간 부여하고, 기간이 끝나면 다시 접근을 제한할 수 있기 때문입니다.

## 상황 4 · 새 권한이 필요함

- 원인: 새로운 업무가 생겼지만 해당 역할의 권한 목록에 필요한 권한이 없어서 요청이 거부됩니다.
- 고칠 파일: `config/roles.json`
- 어떻게 고치나요: 먼저 새 권한이 실제 업무에 필요한지 확인합니다. 계속 필요한 권한이라면 담당자의 승인을 받은 뒤 해당 역할의 권한 목록에 `"자원:행위"` 형식으로 추가합니다. 특정 사용자에게만 잠시 필요한 권한이라면 예외 권한을 사용하는 방법도 검토합니다.
- 고친 뒤 확인: `rbac.py`의 `check_permission()`으로 새 권한을 요청했을 때 허용되는지 확인합니다. 동시에 추가하지 않은 다른 권한은 계속 거부되는지 검사합니다.
- 더 써 보고 싶은 것(선택): 역할에 권한을 추가하면 같은 역할을 가진 사용자 모두에게 영향을 줄 수 있으므로, 권한을 추가하기 전에 영향 범위를 확인해야 합니다.

## 상황 5 · 안 쓰는 권한이 쌓임

- 원인: 업무가 변경되거나 임시로 부여한 권한이 더 이상 필요하지 않은데도 그대로 남아 있기 때문입니다. 불필요한 권한이 쌓이면 사용자가 접근할 수 있는 범위가 넓어집니다.
- 고칠 파일: `config/users.json`, `config/roles.json`, `config/exceptions.json` 및 권한 회수 관련 `revoke_plan.py`, `revoke.py`
- 어떻게 고치나요: 먼저 현재 사용자에게 부여된 권한과 실제 업무에 필요한 권한을 비교합니다. 회수할 권한을 찾은 뒤 `revoke_plan.py`로 회수 계획을 만듭니다. 예외 권한이면 「예외 삭제」, 퇴사자라면 「역할 해제」, 역할에 포함된 불필요한 권한이면 「역할에서 권한 빼기」 방법을 사용합니다. 회수 영향과 승인 여부를 확인한 뒤 적용합니다.
- 고친 뒤 확인: 회수한 권한으로 다시 요청했을 때 거부되는지 확인합니다. 다른 사용자에게 필요한 권한까지 제거되지 않았는지도 검사하고, 회수 이력이 정상적으로 기록되었는지 확인합니다.
- 더 써 보고 싶은 것(선택): 권한은 한 번 부여했다고 계속 유지하는 것이 아니라, 현재 업무에 필요한지 정기적으로 확인해야 합니다. 이를 통해 불필요한 접근 가능성을 줄일 수 있습니다.

## 상황 6 · 민감한 권한을 회수해야 함

- 원인: 데이터를 변경하거나 중요한 시스템을 관리하는 민감한 권한이 더 이상 필요하지 않게 되었습니다. 이런 권한은 잘못 사용되면 피해가 클 수 있지만, 무조건 회수하면 정상 업무에도 영향을 줄 수 있습니다.
- 고칠 파일: `config/sensitive.json`, `revoke_plan.py`, `revoke_approve.py`, `revoke.py`
- 어떻게 고치나요: 먼저 회수 대상과 권한을 확인하고 회수 계획을 만듭니다. `config/sensitive.json`에 등록된 민감한 권한이거나 회수 영향이 2건 이상이면 승인이 필요합니다. `revoke_approve.py`에서 승인 상태를 확인하고, 승인된 계획이나 승인 불필요 계획만 실행하도록 합니다. 승인 대기인 계획은 회수하지 않고 보류해야 합니다.
- 고친 뒤 확인: 회수 전후의 접근 판정 결과를 비교하여 해당 권한이 거부되는지 확인합니다. 승인 대기 항목은 변경되지 않았는지 확인하고, 회수 결과가 이력에 정확하게 기록되었는지도 검사합니다.
- 더 써 보고 싶은 것(선택): 민감한 권한은 보안상 중요하지만 실제 업무에 필요한 경우도 있으므로, 회수하기 전에 영향 범위와 승인 여부를 확인하는 절차가 필요합니다.

## 상황 7 · 새벽 외부 접속, 그리고 정상 직원이 계속 거부됨

- 원인: 사용자가 역할 권한을 가지고 있더라도 요청한 시간이나 접속 위치가 정책에 맞지 않으면 거부될 수 있습니다. 새벽 외부 접속은 허용된 조건을 벗어난 요청일 수 있고, 정상 직원의 반복 거부는 실제 업무 환경과 접근통제 조건이 맞지 않아 발생할 수도 있습니다.
- 고칠 파일: `config/conditions.json` (정상적인 정책 거부라면 수정하지 않고 로그를 먼저 확인)
- 어떻게 고치나요: 먼저 로그에서 사용자, 요청 시각, 접속 위치, 자원, 행위, 거부 사유를 확인합니다. 예를 들어 `gaeun`의 `ACCOUNT:CHANGE` 권한은 09시부터 18시 전까지, `office` 접속에서만 허용됩니다. 새벽이나 외부 네트워크에서 발생한 요청은 기존 정책에 따라 거부합니다. 정상 직원이 업무상 필요한 요청을 계속 거부당한다면 실제 업무 상황을 확인하고 승인받은 뒤 필요한 조건만 조정합니다.
- 고친 뒤 확인: `conditional.py`의 `evaluate_conditional()`로 허용 시간과 접속 위치를 바꿔 가며 검사합니다. 허용된 조건에서는 정상적으로 접근되고, 새벽이나 허용되지 않은 접속 위치에서는 계속 거부되는지 확인합니다.
- 더 써 보고 싶은 것(선택): 정상 직원이 거부된다고 무조건 정책을 완화하면 보안이 약해질 수 있습니다. 먼저 정상적인 업무 요청인지 확인하고 필요한 범위에서만 변경해야 합니다.

## 상황 8 · 매주 어긋남을 확인해야 함

- 원인: 시간이 지나면서 직원이 퇴사하거나 부서가 바뀌고, 예외 권한이 만료되는 등 사용자 정보와 권한 설정이 실제 상황과 달라질 수 있습니다. 또한 반복되는 접근 거부나 비정상적인 요청도 확인할 필요가 있습니다.
- 고칠 파일: `config/week_state.json`, `config/alert.json`, `checklist.py`, `log_summary.py`, `weekly_report.py` 및 점검 결과에 따라 문제가 발견된 권한 설정 파일
- 어떻게 고치나요: 먼저 `checklist.py`로 퇴사자 계정, 만료된 예외, 부서와 역할이 일치하는지 점검합니다. 다음으로 `log_summary.py`를 사용해 요청 로그를 분석하고 전체 요청 수, 허용과 거부 수, 거부율, 거부 사유, 반복 거부 사용자를 집계합니다. 마지막으로 `weekly_report.py`에서 점검 결과와 로그 집계를 합쳐 주간 보고서를 생성합니다. 문제가 발견된 항목은 원인을 확인한 뒤 필요한 조치를 결정합니다.
- 고친 뒤 확인: 2026-11-02 주간 보고서에서는 전체 요청 40건 중 허용 24건, 거부 16건으로 거부율이 40%였습니다. 경고 기준인 30%를 초과하여 경고가 발생했고, `dami`의 퇴사자 계정과 `junho`의 부서·역할 불일치가 확인되었습니다. 이런 항목이 보고서에 정확하게 표시되는지 확인하고, 실제 조치 후에는 다시 점검하여 문제가 해결되었는지 검사합니다.
- 더 써 보고 싶은 것(선택): 거부율이 0%라고 해서 무조건 안전한 것은 아닙니다. 서버가 멈춰 로그가 수집되지 않아도 0%가 나올 수 있으므로 전체 요청 수와 로그 수집 상태를 함께 확인해야 합니다.
