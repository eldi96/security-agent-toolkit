## 5교시 · 설정 파일이 고장 나도 거부하기

### 문제 5-1 · 설정 파일을 안전하게 읽는 함수 `load_json` 만들고, 고장 두 가지로 시험하기

- (가) 실행한 출력 전체를 붙여 넣고, 경고 두 줄이 각각 어떤 오류 때문에 나왔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체 ② 경고 두 줄이 각각 어떤 오류 때문에 나왔는지
  - 답:

```
config/users.json -> 사용자 6 명을 읽음, 판정을 계속한다
[경고] 설정 파일 없음: config/users_typo.json
config/users_typo.json -> 사용자 0 명, 등록된 사용자가 없다
[경고] 설정 파일 깨짐: config/users_broken.json
config/users_broken.json -> 사용자 0 명, 등록된 사용자가 없다
```
    ② 경고 발생 원인

    [경고] 설정 파일 없음: config/users_typo.json 파일이 존재하지 않아 FileNotFoundError가 발생했다.

    [경고] 설정 파일 깨짐: config/users_broken.json 파일의 JSON 형식이 올바르지 않아 json.JSONDecodeError가 발생했다.

    두 경우 모두 except에서 빈 딕셔너리를 기본값으로 반환하여 프로그램이 중단되지 않고 사용자 0명으로 처리되었다.

- (나) 🔍 실패했을 때 프로그램을 멈추지 않고 빈 설정을 리턴하는 것이, 오류로 멈추는 것보다 왜 안전한가요? 「멈춘 뒤 현장에서 생기는 일」을 넣어 적어 주세요.
  - 쓸 내용: ① 빈 설정을 리턴하는 이유 ② 멈춘 뒤 현장에서 생기는 일
  - 답:
    ① 빈 설정을 리턴하는 이유
      설정 파일이 없거나 손상되어도 프로그램이 중단되지 않고 접근통제 판정을 계속할 수 있다.
      빈 설정을 사용하면 등록된 사용자나 권한이 없는 것으로 판단하여 접근을 기본적으로 거부할 수 있다.
      이는 오류가 발생했을 때 권한을 임의로 허용하지 않는 Fail-Closed(안전한 거부) 원칙에 해당한다.

      ② 프로그램이 멈췄을 때 현장에서 생기는 일
      접근통제 프로그램이 중단되면 정상 사용자도 정산 시스템에 접근하지 못해 업무가 지연될 수 있다.
      운영자가 장애를 해결하기 위해 접근통제 기능을 임시로 해제하거나 우회할 위험이 있다.
      반면 빈 설정으로 계속 실행하면 접근을 거부하면서 경고를 남길 수 있어 보안 상태를 유지하며 복구 작업을 진행할 수 있다.

- (다) 🔍 설정 파일이 깨져서 모두 거부되면 정산 업무가 멈춥니다. 운영자가 이 상황을 빨리 알고 복구하려면 판정 프로그램에 무엇을 더하겠습니까? 두 가지 이상 적고, 그중 가장 먼저 할 것을 고른 이유를 적어 주세요.
  - 쓸 내용: ① 더할 것 두 가지 이상 ② 가장 먼저 할 것과 그 이유
  - 답:
      ① 추가할 기능
      자동 경고 알림: 설정 파일을 읽지 못하면 운영자에게 즉시 알림을 전송한다.
      오류 로그 기록: 오류 발생 시각, 파일 경로, 오류 종류를 기록하여 원인을 추적할 수 있도록 한다.
      정상 설정 백업 및 복구: 마지막으로 검증된 정상 설정을 별도로 보관하고, 운영자가 확인한 뒤 신속하게 복구할 수 있도록 한다.
      설정 파일 유효성 검사: JSON 문법과 필수 항목을 검사하여 잘못된 설정이 운영 환경에 적용되지 않도록 한다.

      ② 가장 먼저 할 것과 이유
      가장 먼저 추가할 기능은 자동 경고 알림이다.
      설정 파일이 손상되어 모든 접근이 거부되더라도 운영자가 상황을 알지 못하면 장애가 장시간 지속될 수 있다. 따라서 오류 발생 즉시 운영자에게 알림을 보내 빠르게 원인을 파악하고 정상 설정으로 복구할 수 있도록 해야 한다.
      복구가 완료되기 전까지는 접근통제를 우회하지 않고 기본 거부 정책을 유지하여 보안 사고를 예방해야 한다.

## 6교시 · 테스트 케이스 설계

### 문제 6-1 · 꼭 지켜야 할 네 가지를 테스트로 설계하고, 팀원의 제안을 시험하기

- (가) `test_policy_extra.py` 를 실행한 출력 전체를 붙여 넣고, 실패한 줄 번호와 `AssertionError:` 뒤에 나온 글자를 적어 주세요.
  - 쓸 내용: ① `test_policy_extra.py` 출력 전체 ② 실패한 줄 번호 ③ `AssertionError:` 뒤의 글자
  - 답:
```
    5 통과
    Traceback (most recent call last):
      File "C:\Users\User\Documents\security-agent-toolkit\access_control\test_policy_extra.py", line 16, in <module>
        assert ok == True, "6. 만료 정각에도 허용되어야 한다(팀원 제안)"
    AssertionError: 6. 만료 정각에도 허용되어야 한다(팀원 제안)
```
  - 실패한 줄 번호 line 14, "6. 만료 정각에도 허용되어야 한다(팀원 제안)"

- (나) 🔍 그 실패는 코드가 틀렸다는 뜻인가요, 제안이 우리가 정한 만료 규칙과 다르다는 뜻인가요? 근거를 적어 주세요.
  - 쓸 내용: ① 코드가 틀렸는지, 제안이 정책과 다른지 ② 우리가 정한 만료 규칙과 3번 테스트 결과를 근거로 한 이유
  - 답:
        ① 실패 원인
        코드가 틀린 것이 아니라 팀원의 제안이 기존 만료 규칙과 다르기 때문에 발생한 실패이다.

        ② 판단 근거
        기존 정책은 now < expires 조건을 사용하여 현재 시각이 만료 시각보다 이전일 때만 임시 권한을 허용한다.
        3번 테스트에서는 seoyeon의 예외 1번을 17:59에 허용하고, 만료 정각인 18:00에는 거부하도록 검증했다.
        반면 팀원의 6번 테스트는 18:00에도 접근을 허용해야 한다고 주장하므로 기존 정책과 충돌한다.

        따라서 6번 테스트의 실패는 기존 보안 정책이 정상적으로 적용되고 있음을 보여 주는 결과이며, 팀원의 제안을 반영하려면 먼저 만료 규칙 변경에 대한 검토와 승인이 필요하다.

- (다) 🔍 정책 코드를 바꿀 때마다 `test_policy.py` 의 1 ~ 4번 테스트를 돌리지 않으면 어떤 사고가 날 수 있나요? 네 개 중 하나를 골라, 그 테스트가 막아 주는 사고를 구체적인 장면으로 적어 주세요.
  - 쓸 내용: ① 고른 테스트 ② 그 테스트가 막아 주는 사고 장면
  - 답:
      ① 선택한 테스트
      3번 테스트 — 임시 권한 만료 시각 검증
      17:59에는 예외 1번을 허용한다.
      만료 정각인 18:00부터는 접근을 거부한다.

      ② 테스트가 막아 주는 사고 장면
      정산 업무를 위해 seoyeon에게 오후 6시까지 임시 조회 권한을 부여했다고 가정한다.
      이후 개발자가 정책 코드를 수정하면서 now < expires를 now <= expires로 변경하거나 만료 시각 검사를 누락하면, 만료된 권한으로도 정산 정보에 접근할 수 있는 문제가 발생할 수 있다.
      정책 변경 후 3번 테스트를 실행하면 만료 시각에 접근이 허용되는 오류를 발견할 수 있다. 이를 통해 임시 권한이 정해진 기간을 초과하여 사용되는 것을 방지하고, 최소 권한 원칙과 권한 만료 정책을 유지할 수 있다.
      따라서 정책 코드를 변경할 때마다 기존 테스트를 다시 실행하는 **회귀 테스트(Regression Test)**가 필요하다.
