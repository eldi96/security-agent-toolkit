## 2교시 · 권한 요청서 만들기

### 문제 2-1 · 요청서를 만들어 목록에 모으고, 접수할 수 없는 요청 걸러 내기

- (가) 실행한 출력 전체를 붙여 넣고, 접수되지 않은 세 건이 각각 `create_request` 의 어느 `if` 조건 때문에 접수되지 않았는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 접수되지 않은 세 건 각각이 걸린 `if` 조건
  - 답:

```
    --- 단계 1: 접수 - 요청 일곱 건을 하나씩 넣는다
    seoyeon SETTLE QUERY -> 접수됨, 요청 번호 1
    gaeun SALES QUERY -> 접수됨, 요청 번호 2
    dami SALES QUERY -> 접수됨, 요청 번호 3
    junho SETTLE QUERY -> 접수됨, 요청 번호 4
    hana SALES QUERY -> 접수 안 됨: 등록되지 않은 사용자
    seoyeon ACCOUNT QUERY -> 접수 안 됨: 이유가 없음
    gaeun ACCOUNT QUERY -> 접수 안 됨: 만료 시각이 이미 지났음

    --- 단계 2: 점검 - 요청서 목록
    1 seoyeon SETTLE:QUERY reviewing
    2 gaeun SALES:QUERY reviewing
    3 dami SALES:QUERY reviewing
    4 junho SETTLE:QUERY reviewing
```
    ② 접수되지 않은 세 건의 원인
    사용자	접수 거부 조건	이유
    hana	if user not in USERS:	사용자 목록에 등록되지 않은 계정
    seoyeon	if reason == "":	요청 사유가 빈 문자열
    gaeun	if until <= received_at:	희망 만료 시각이 접수 시각보다 이전

    정리: 총 7건 중 4건이 접수되고 3건이 거부되었다. 단, dami와 junho는 퇴사자이지만 현재 접수 함수에서는 재직 여부를 검사하지 않으므로 요청서가 접수된다. 접수 성공이 접근 권한 승인을 의미하지는 않는다.
---
- (나) 🔍 요청서의 `until`(희망 만료 시각)은 요청자가 직접 적습니다. 요청자가 적은 기간을 그대로 믿고 승인해도 될까요? 승인하기 전에 확인할 것을 두 가지 이상 적어 주세요.
  - 쓸 내용: ① 그대로 믿어도 되는지 ② 승인 전에 확인할 것 두 가지 이상
  - 답:
      그대로 승인하면 안 된다. 요청자가 작성한 기간은 희망 기간일 뿐이며, 실제 업무에 필요한 최소 기간인지 검토해야 한다.

      승인 전에 확인할 사항은 다음과 같다.
      1. 업무 필요성: 요청 사유가 실제 업무와 관련이 있는지, 해당 권한이 반드시 필요한지 확인한다.
      2. 최소 권한 및 기간: 요청한 자원과 작업이 필요한 범위인지, 만료 시각이 업무 수행에 필요한 최소 기간인지 확인한다.
      3. 사용자 상태: 요청자가 현재 재직 중인지, 계정이 비활성화되거나 퇴사 처리되지 않았는지 확인한다.
      4. 승인 권한: 해당 자원에 대한 권한을 승인할 수 있는 담당자가 검토했는지 확인한다.
      결론: 요청 접수 단계에서는 형식과 필수 정보를 확인하고, 승인 단계에서는 사용자 상태·업무 필요성·권한 범위·만료 기간을 검증해야 한다. 이를 통해 불필요한 권한 부여와 장기간의 무단 접근 위험을 줄일 수 있다.

## 3교시 · 승인과 반려

### 문제 3-1 · 승인 · 반려 함수 만들고, 두 번째 처리가 막히는지 확인하기

- (가) 실행한 출력 전체를 붙여 넣고, 막힌 세 줄이 각각 왜 막혔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 막힌 세 줄 각각의 이유
  - 답:

```
    --- 단계 1: 처리 - 본인 요청 시험 한 건, 승인 · 반려 여섯 건을 처리한다
    1 본인 승인 -> False 본인 요청은 처리할 수 없음
    1 승인 -> True 승인
    2 반려 -> True 반려
    3 승인 -> True 승인
    4 승인 -> True 승인
    1 승인 -> False 검토 중이 아님
    2 승인 -> False 검토 중이 아님

    --- 단계 2: 점검 - 요청서 목록
    1 seoyeon approved None
    2 gaeun rejected security_manager
    3 dami approved None
    4 junho approved None
```
    ② 막힌 세 줄의 이유
    막힌 처리	이유
    1 본인 승인 → False	요청자 seoyeon이 자신의 요청을 직접 승인하려 했기 때문에 차단되었다.
    1 승인 → False	1번 요청은 이미 approved 상태이므로 다시 승인할 수 없다.
    2 승인 → False	2번 요청은 이미 rejected 상태이므로 승인할 수 없다.

    추가 확인: 승인 함수에 request["appover"] = approver라는 오타가 있어 승인된 요청의 처리자가 None으로 출력되었다. request["approver"] = approver로 수정해야 한다.

- (나) 🔍 이미 승인한 요청서를 다시 승인하지 못하게 막는 이유는 무엇인가요? 막지 않으면 어떤 일이 생길 수 있나요?
  - 쓸 내용: ① 막는 이유 ② 막지 않을 때 생길 수 있는 일
  - 답:
    ① 막는 이유
    이미 처리된 요청의 상태가 다시 변경되지 않도록 하여 승인 절차의 무결성과 처리 이력의 신뢰성을 유지하기 위해서이다.

    ② 막지 않을 때 생길 수 있는 일
    동일한 요청이 중복 승인되어 권한이 반복 부여되거나, 이미 반려된 요청이 승인 상태로 변경될 수 있다. 또한 처리 이력이 덮어써져 누가 언제 승인했는지 추적하기 어려워질 수 있다.

- (다) 🔍 `approve_request` 에서 `request["user"] == approver` 검사를 뺀다면 어떤 위험이 생길까요? 요청자가 친구에게 대신 승인해 달라고 부탁하면 이 검사로는 막을 수 없습니다. 이런 경우를 막으려면 무엇이 더 필요할까요?
  - 쓸 내용: ① 검사를 뺐을 때의 위험 ② 더 필요한 장치 한 가지 이상
  - 답:
      ① 검사를 뺐을 때의 위험
      요청자가 자신의 권한 신청을 직접 승인할 수 있게 된다. 이는 직무 분리(SoD, Segregation of Duties) 원칙을 위반하며, 승인 절차를 거치지 않고 불필요한 권한을 획득하는 위험으로 이어진다.

      ② 더 필요한 장치
      RBAC 기반 승인자 권한 검증이 필요하다. 단순히 요청자와 승인자의 이름이 다른지만 확인하는 것이 아니라, 승인자에게 실제 승인 권한이 있는지도 검사해야 한다.
      또한 친구와 공모하는 상황에 대비해 중요한 권한은 2인 이상의 독립적인 승인을 요구하고, 승인 사유와 처리자를 감사 로그에 기록하는 방법을 적용할 수 있다.
      즉, 본인 승인 금지 + 승인자 권한 검증 + 중요 권한의 다중 승인을 적용하면 무단 승인과 공모 위험을 줄일 수 있다.

## 4교시 · 정책 확인 후 예외 권한 부여

### 문제 4-1 · 승인된 요청서를 정책으로 확인하고 예외 권한 부여하기

- (가) 실행한 출력 전체를 붙여 넣고, 부여를 시도한 네 건이 각각 어떻게 됐는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 네 건 각각의 결과
  - 답:

```
    --- 단계 1: 판정 - 부여 전
    1 seoyeon SETTLE:QUERY -> False 권한 없음
    2 gaeun SALES:QUERY -> False 권한 없음
    3 dami SALES:QUERY -> False 퇴사한 계정
    4 junho SETTLE:QUERY -> True 역할 권한

    --- 단계 2: 부여 - 요청서마다 부여를 시도한다
    1 seoyeon granted -> True 부여
    2 gaeun rejected -> False 승인되지 않음
    3 dami approved -> False 부여하지 않음(퇴사한 계정)
    4 junho approved -> False 부여하지 않음(허용)
    부여된 예외 번호: 6

    --- 단계 3: 점검 - 부여 후
    1 seoyeon SETTLE:QUERY -> True 예외 6번
    2 gaeun SALES:QUERY -> False 권한 없음
    3 dami SALES:QUERY -> False 퇴사한 계정
    4 junho SETTLE:QUERY -> True 역할 권한
```
    ② 네 건 각각의 결과
    요청자	결과	이유
    seoyeon	부여 성공	승인된 요청이고 기존 역할에 해당 권한이 없어 임시 예외 6번을 부여받았다.
    gaeun	부여 실패	요청 상태가 rejected이므로 승인되지 않은 요청은 부여할 수 없다.
    dami	부여 실패	요청은 승인되었지만 퇴사한 계정이므로 정책 검사에서 차단되었다.
    junho	부여 실패	이미 SETTLE:QUERY 역할 권한을 가지고 있으므로 추가 예외를 부여할 필요가 없다.

- (나) 🔍 승인자가 승인한 3번 요청(`dami`)을 코드가 부여하지 않았습니다. 코드의 이 확인이 없었다면 어떤 일이 생겼을까요? 승인자가 이 문제를 미리 막기 어려운 이유도 적어 주세요.
  - 쓸 내용: ① 확인이 없을 때 생기는 일 ② 승인자가 미리 막기 어려운 이유
  - 답:
      ① 확인이 없을 때 생기는 일
      퇴사한 dami에게도 임시 예외 권한이 등록될 수 있다. 현재 접근 판정 코드에서는 퇴사 계정을 별도로 차단하지만, 이 검사가 누락되거나 정책이 변경된다면 퇴사자가 내부 정보에 접근할 위험이 생긴다.

      ② 승인자가 미리 막기 어려운 이유
      승인자가 모든 사용자의 최신 재직 상태와 권한 정보를 실시간으로 파악하기 어렵기 때문이다. 또한 승인 이후 실제 권한이 부여되기 전까지 사용자의 재직 상태가 변경될 수도 있다.
      따라서 승인 단계와 별개로 실제 권한 부여 시점에도 재직 여부와 기존 권한을 다시 검사해야 한다.

- (다) 🔍 부여한 예외의 만료 시각에는 요청서의 희망 만료 시각을 그대로 썼습니다. 그 시각이 지나면 이 예외는 어떻게 될까요? 만료된 예외를 정리하는 점검은 누가 얼마나 자주 하면 좋을까요?
  - 쓸 내용: ① 만료 뒤 예외가 어떻게 되는지 ② 점검을 누가 얼마나 자주 할지
  - 답:
    ① 만료 뒤 예외가 어떻게 되는지
    만료 시각이 지나면 find_exception()의 now < expires 조건을 만족하지 못하므로 해당 예외는 더 이상 접근 허용에 사용되지 않는다.
    다만 예외가 자동으로 삭제되는 것은 아니므로 만료된 데이터는 EXCEPTIONS 목록에 남아 있게 된다.

    ② 점검을 누가 얼마나 자주 할지
    보안 담당자가 관리 책임을 맡고, 자동화된 프로그램으로 최소 하루 한 번 만료된 예외를 점검하는 것이 적절하다.
    실제 접근 요청이 발생할 때는 매번 만료 여부를 확인해 만료된 권한이 사용되지 않도록 해야 한다. 만료된 예외는 비활성화하고, 감사에 필요한 기록은 별도로 보관하는 것이 좋다.
