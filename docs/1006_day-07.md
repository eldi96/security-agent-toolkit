# Day 07. LLM API와 도구 실행형 에이전트

> 2026-10-06 · AI 자동화를 위한 Python

## 오늘의 학습

LLM API에 POST 요청을 보내고 응답의 중첩 JSON에서 필요한 문장을 꺼내는 과정을 배웠다. 프롬프트와 응답 형식을 다룬 뒤, LLM이 도구 이름을 선택하고 Python 코드가 실제 함수를 실행하는 에이전트 구조로 확장했다. Registry·Router를 분리하고 위험한 작업에는 사람의 승인을 넣었다.

## 학습 내용

### LLM API의 요청과 응답

LLM에게 질문을 보내는 작업도 API를 이용한 HTTP 요청으로 연결했다. 요청 URL, 인증 정보가 담긴 헤더, 모델 이름과 메시지가 담긴 본문을 구분했다. 응답은 중첩된 JSON으로 오기 때문에 `choices` 같은 목록과 그 안의 `message`, `content`를 단계별로 읽는 구조를 살펴봤다. 실제 응답 필드는 API마다 다를 수 있다.

`system`과 `user` 역할, 프롬프트 작성, few-shot 예시, `temperature` 설정도 배웠다. 자동화에서는 사람이 읽기 좋은 문장보다 **코드가 안정적으로 읽을 수 있는 응답 형식**이 중요하다. JSON으로 답하라고 요청하더라도 코드 블록 표시나 공백이 섞일 수 있어 문자열을 정리하고 `json.loads()`로 파싱하는 과정이 필요했다.

### LLM의 판단과 Python 실행 분리

LLM이 도구를 사용한다는 말은 모델이 내 컴퓨터의 Python 함수를 직접 실행한다는 뜻이 아니다. 모델은 어떤 도구를 어떤 인자로 사용할지 선택하고, 실제 함수 실행은 별도의 Python 코드가 담당한다. 처음에는 `if/elif`로 도구 이름마다 실행할 함수를 분기할 수 있지만 도구 수가 늘면 관리가 복잡해진다.

이 문제를 줄이기 위해 Registry와 Router 구조를 사용했다. Registry는 도구 이름을 키로, 실제 함수 객체를 값으로 저장한 딕셔너리다. Router는 선택 결과의 `tool` 값을 읽고 Registry에서 함수를 찾아 인자를 전달한다. 함수 이름 뒤에 `()`를 붙이지 않고 저장해야 실행 결과가 아니라 함수 자체를 연결할 수 있다.

### 승인 게이트와 사람의 개입

IP 조회처럼 정보만 읽는 도구와 계정 잠금·IP 차단처럼 시스템 상태를 바꾸는 도구는 위험도가 다르다. 위험한 도구 이름을 승인 목록에 넣고, 실행 전에 사용자에게 확인받는 Human in the Loop 구조를 만들었다. 승인이 없으면 `held` 같은 상태로 보류하는 방식으로 자동화의 실행 범위를 통제했다.

## 실습 흐름

LLM 요청 → 응답 파싱 → 도구 선택 → Registry 조회 → Router 실행 → 승인 게이트

## 기억할 코드

**도구 이름과 함수 연결**

```python
tool_registry = {"lookup_ip": lookup_ip,
                 "count_failed_logins": count_failed_logins}
```

**선택한 도구 실행**

```python
name = choice["tool"]
func = tool_registry.get(name)
if func is not None:
    result = func(choice["args"])
```

## 실습에서 연결된 내용

이날 가장 중요한 구분은 **LLM은 도구를 선택하고 Python은 실행한다**는 점이었다. Registry는 이름과 함수를 연결하는 저장소, Router는 그 이름을 이용해 실행하는 흐름이며, 위험한 작업은 그 사이에 승인 단계를 추가하는 방식으로 확장했다.

## 오늘 막혔던 부분

Registry가 별도의 Python 기능인지, `tool_registry.get(name)`의 `name`이 어디에서 온 값인지 헷갈렸다. Registry는 함수 객체를 담은 딕셔너리이고, `name`은 LLM의 선택 결과에서 꺼낸 문자열이라는 점을 확인했다. 승인 목록에는 함수가 아니라 도구 이름 문자열을 넣는다는 차이도 정리했다.
