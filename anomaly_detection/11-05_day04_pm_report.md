## 5교시 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

### 문제 5-1 · 서로 다른 로그를 한 사용자 기준으로 연결해 60분 안의 사건 찾기

- (가) 실행한 출력 전체를 붙여 넣고, 연결된 사건의 사용자와 이유를 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② 연결된 사건의 사용자 ③ 이유
  - 답:

    - **연결된 사용자:** `gaeun`.
    - **이유:** 서로 다른 로그 3종류(web·server·saas)의 이벤트가 분 단위 계산으로 41분 안에 모여, 로그 2종류 이상·60분 이내 조건을 모두 만족했다.

```
--- 단계 1: IP 로 사용자를 알 수 있는 웹 실패 이벤트 1 개
--- 단계 2: 사용자별로 시간순으로 놓은 이벤트 24 개
gaeun 의 이벤트 (시각 · 로그 · 행동 · 결과)
2026-11-02 09:33:51 web GET /admin 실패
2026-11-02 10:05:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:09:00 server ACCOUNT:CHANGE 실패
2026-11-02 10:12:55 saas login 성공
2026-11-02 10:14:00 server ACCOUNT:CHANGE 실패
--- 단계 3: 60 분 안에 서로 다른 로그로 연결된 사건
{'user': 'gaeun', 'reason': '서로 다른 로그3종류 .41분 안'}
--- 단계 4: 로그 종류는 여럿이지만 시간 차가 60분을 초과해 연결되지 않은 사용자
{'user': 'seoyeon', 'source_count': 2, 'span_minutes': 555}
```

- (나) 🔍 단계 2에 나온 gaeun 의 이벤트 5개는 어느 로그(`source`)에서 왔고, 왜 한 사건으로 연결됐나요? 이 사건만으로 공격이라고 확정할 수 있는지도 적어 주세요.
  - 쓸 내용: ① gaeun 이벤트 5개의 로그(source) ② 연결된 까닭 ③ 공격이라고 확정할 수 있는지와 그 근거(단계 2 의 action · result 와 오전 2교시 판정 이유)
  - 답:

    - **로그 구성:** web 1개(`/admin` 실패), server 3개(`ACCOUNT:CHANGE` 실패), saas 1개(`login` 성공)이다.
    - **연결 근거:** 성공한 SaaS 로그인의 IP로 웹 이벤트에 gaeun을 연결했고, 같은 사용자에게 3종류의 로그가 41분 안에 모였다. IP에 의한 사용자 연결은 실제 동일 인물인지 추가 확인이 필요한 추정이다.
    - **공격 확정 여부:** 확정할 수 없다. 관리자 경로와 계정 변경 실패가 반복돼 의심스럽지만, 오전 재판정에서 gaeun의 계정 변경은 규칙상 허용이었다. 서버의 실제 적용 권한·설정과 거부 이유를 확인하고 SaaS 로그인도 본인 행동인지 조사해야 한다.

- (다) 🔍 seoyeon 은 서로 다른 로그에 나오지만 연결되지 않았습니다. 단계 4 의 두 숫자(로그 종류 수와 처음부터 마지막까지의 분)로 두 조건을 비교해 연결되지 않은 이유를 설명하고, 하나의 사건으로 연결하지 않아서 탐지하지 못할 수 있는 것을 오전 3교시 출력에서 seoyeon 이 나온 규칙과 연결해 적어 주세요.
  - 쓸 내용: ① 연결되지 않은 이유(두 조건과 단계 4 의 두 숫자) ② 연결하지 않아서 탐지하지 못할 수 있는 것
  - 답:

    - **제외 이유:** 로그는 2종류로 최소 2종류 조건을 만족하지만, 처음부터 마지막까지 555분으로 60분 이내 조건을 만족하지 못했다.
    - **놓칠 수 있는 흐름:** 오전 SaaS 탐지에서 seoyeon은 평소와 다른 IP 로그인과 대량 다운로드에 해당했다. 현재 규칙은 사용자 전체 이벤트의 처음·마지막 간격을 보므로, 일부 이벤트가 짧은 시간에 이어져도 전체 간격이 길면 연결하지 못한다. 다른 로그의 실패와 낯선 IP 로그인·다운로드가 관련된 사건일 가능성을 놓칠 수 있다.

## 6교시 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

### 문제 6-1 · 탐지된 규칙에 점수를 매겨 등급과 이유를 day03_risk_scores.json 에 저장하기

- (가) 실행한 출력 전체를 붙여 넣고, high · mid · low 에 각각 어떤 대상이 들어갔는지 적어 주세요.
  - 쓸 내용: ① 출력 전체(코드 상자에 붙여 넣기) ② high 에 들어간 대상 ③ mid 에 들어간 대상 ④ low 에 들어간 대상
  - 답:

    - **high:** `dami` 60점.
    - **mid:** `seoyeon` 45점, `gaeun` 40점, `jiwoo` 35점.
    - **low:** `198.51.100.90` 30점. 총 5건을 JSON 파일에 저장했다.

```
--- 단계 1: 탐지된 규칙 8 건
--- 단계 2: 대상별 점수
entity
dami             60
seoyeon          45
gaeun            40
jiwoo            35
198.51.100.90    30
Name: points, dtype: int64
--- 단계 3: day03_risk_scores.json 에 5 건 저장
--- 단계 4: 등급 · 대상 · 점수 · 이유
high dami 60 ['퇴사한 계정']
mid seoyeon 45 ['평소와 다른 IP', '대량 다운로드']
mid gaeun 40 ['규칙은 허용인데 서버가 거절', '여러 로그 연결']
mid jiwoo 35 ['업무 시간 밖 로그인', '평소와 다른 IP']
low 198.51.100.90 30 ['경로 스캔']
```

- (나) 🔍 seoyeon 의 점수가 어떤 규칙의 점수를 더해 나왔는지 적고, 점수만 저장하지 않고 이유(`reasons`)를 함께 저장하는 까닭을 적어 주세요.
  - 쓸 내용: ① seoyeon 점수를 이룬 규칙과 점수 ② 이유를 함께 저장하는 까닭
  - 답:

    - **점수 구성:** 평소와 다른 IP 20점 + 대량 다운로드 25점 = **45점(mid)**이다. 여러 로그 연결 조건에는 해당하지 않아 그 점수는 더하지 않았다. 같은 대상·같은 규칙은 이벤트가 여러 개여도 한 번만 더한다.
    - **이유를 저장하는 까닭:** 점수만으로는 어떤 행동 때문에 등급이 정해졌는지 알 수 없다. 규칙 이름을 함께 남겨야 담당자가 근거 로그를 찾아 조사하고, 오탐 여부와 점수 기준의 적절성을 검토할 수 있다.

- (다) 🔍 198.51.100.90 은 경로 스캔 하나에 해당하지만 low 입니다. low 는 점수 기준상 낮은 등급이라는 뜻입니다. low 인 이유를 점수와 기준으로 설명하고, 이 IP 의 기록을 무시해도 되는지 샘플의 값(그 IP 의 요청 3개의 `result`)으로 판단해 적어 주세요.
  - 쓸 내용: ① low 인 이유(점수와 기준) ② 무시해도 되는지(오전 4교시 find_scan_ips 결과나 normalized_events.json 의 이 IP 요청 시각 · 경로 · 결과를 근거로)
  - 답:

    - **low인 이유:** 경로 스캔 규칙 30점만 해당하며, mid 기준인 35점보다 낮기 때문이다. high 기준은 60점 이상이다.
    - **무시 여부:** 무시하면 안 된다. 09:20:10~09:20:12에 `/.env`, `/wp-login.php`, `/phpmyadmin`을 1초 간격으로 요청했고 결과는 모두 실패였다. 설정 파일·관리 화면을 탐색한 흔적일 수 있으며, 실패했다고 시도가 안전한 것은 아니다. low는 이 점수 체계의 조사 우선순위가 낮다는 뜻이지 공격이 아니라는 판정은 아니다.
