## 4교시 · 4과목 총정리: 상황마다 원인과 고치는 방법 정리하기

### 문제 4-1 · 상황 8개의 원인과 고치는 방법을 내 말로 정리하기

**상황 정리** — 상황 1 · 2 · 3 · 4 · 7 · 8 중 4개 이상 씁니다. 상황 5 · 6 은 본보기입니다.

#### 상황 1 · 설정 파일 주소를 연달아 요청했는데 「의심」이 아니라 「오류」로 분류됨
- 원인: 규칙 문제. 404인 탐색 요청은 기존의 401·403 또는 `/admin` 조건에 맞지 않는다.
- 고칠 파일: `log_classify.py`의 `is_suspicious`.
- 어떻게 고치나요: `/.env`·`/wp-login`·`/phpmyadmin` 경로 조건을 추가한다. 목록 밖 탐색은 IP별 반복·경로 변화를 보는 별도 규칙으로 보완한다.
- 고친 뒤 확인: 같은 샘플에서 정상 15·오류 2·의심 11로 바뀌는지 확인한다. 이는 수정 후 예상값이다.
- 담당자가 가장 먼저 할 일(선택): 같은 IP의 다른 요청과 성공한 접근이 있는지 확인한다.

#### 상황 2 · 로그 30줄이 이벤트 28개가 됨
- 원인: 데이터 문제. 요청이 잘린 줄과 `-`만 있는 줄은 읽을 수 없어 이벤트가 되지 못했다.
- 고칠 파일: 원본 `access_sample.log`와 로그 생성·수집 설정을 점검한다. 정규화 코드의 깨진 줄 제외는 정상 동작이다.
- 어떻게 고치나요: 실패 원문을 보관하고 잘림 원인을 조사한다. 없는 값을 임의로 채우지 않는다.
- 고친 뒤 확인: 읽기 성공 28줄 + 실패 2줄 = 원본 30줄인지 확인한다.
- 담당자가 가장 먼저 할 일(선택): 읽기 실패한 두 줄의 원문을 확인한다.

#### 상황 3 · 웹 서버 로그에서 사용자를 알 수 있는 요청이 1개뿐
- 원인: 데이터 문제. 웹 로그에는 이름이 없고, SaaS 성공 로그인과 IP로 연결되는 웹 실패는 gaeun의 1건뿐이다.
- 고칠 파일: 웹 애플리케이션 인증 로그 설정과 정규화 코드, `correlation.py`의 사용자 연결 부분.
- 어떻게 고치나요: 인증된 사용자 식별자를 로그에 남겨 연결한다. 사용자를 모르면 IP 기준으로 조사하며, 공유 IP를 동일 인물이라고 단정하지 않는다.
- 고친 뒤 확인: 식별 가능한 이벤트 수와 매핑 정확도를 확인하고 IP 기반 탐지도 유지되는지 본다.
- 담당자가 가장 먼저 할 일(선택): `203.0.113.50`과 연결되는 인증 기록을 찾는다.

#### 상황 4 · 두 로그에 나오는 seoyeon 이 연결되지 않음
- 원인: 규칙 문제. 로그는 2종류지만 하루 전체의 첫·마지막 간격이 555분이어서 60분 조건을 넘는다.
- 고칠 파일: `correlation.py`의 `find_chains`.
- 어떻게 고치나요: 사용자 전체 간격 대신 사용자별 60분 구간마다 로그 종류를 검사하도록 보완한다. 기준만 크게 올리면 관계없는 활동도 묶일 수 있다.
- 고친 뒤 확인: 17:38 로그인부터 18:20 서버 실패까지 42분 구간이 연결되는지, 기존 gaeun 연결도 유지되는지 확인한다.
- 담당자가 가장 먼저 할 일(선택): 낯선 IP 로그인·다운로드·서버 실패를 시간순으로 조사한다.

#### 상황 5 · 협력사 사무실에서 접속한 정상 접속에 알림이 남 (본보기)
- 원인: 규칙 문제입니다. `SaaS 평소와 다른 IP` 규칙은 지난 접속 기록에 없는 IP 이면 모두 알림을 냅니다. 협력사 사무실 IP 203.0.113.80 에서 jiwoo(A4)와 seoyeon(A5)이 출장 · 외근 중에 접속했는데, 조사해 보니 모두 정상 접속이었습니다.
- 고칠 파일: `tuning.py` (`TRUSTED_IPS` 와 `apply_exception`)
- 어떻게 고치나요: 새로 넣고 뺍니다. 믿는 IP 리스트에 `203.0.113.80` 한 개를 넣고, `SaaS 평소와 다른 IP` 규칙의 알림 가운데 그 IP 에서 온 것만 알림 표에서 뺍니다. 다른 규칙의 알림(A3 · A6)은 같은 IP 여도 빼지 않습니다.
- 고친 뒤 확인: 오탐이 4개에서 2개로 줄었는지 보고, 빠진 알림 가운데 진짜 문제(`real` 이 `True`)가 0개인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.80 이 협력사 사무실 IP 가 맞는지 출장 · 외근 일정과 비교해 확인합니다.

#### 상황 6 · 로그인 규칙이 낸 알림이 평가에서 빠짐 (본보기)
- 원인: 데이터 문제입니다. 로그인 규칙이 낸 알림 A8 은 `login_alerts.json` 에 따로 저장돼 있고, 첫 평가에 쓴 `review_alerts.json` 의 알림 7개에는 들어 있지 않습니다. 평가는 알림 7개만 보고 「알림이 난 진짜 문제」를 세므로, A8 이 가리키는 P4 가 미탐으로 셉니다. 규칙은 알림을 이미 냈지만 평가에 들어가지 못했습니다.
- 고칠 파일: `final_check.py` (`merge_alerts`)
- 어떻게 고치나요: 새로 넣습니다. `pd.concat([alerts, login_alerts])` 로 두 알림 표를 위아래로 이어 붙인 뒤 합친 표로 평가합니다. A8 은 조사해 보니 진짜 문제(`real` 이 `True`)여서 오탐은 늘지 않습니다.
- 고친 뒤 확인: 미탐이 2개(P4 · P5)에서 1개(P5)로 줄고 오탐은 2개 그대로인지 봅니다.
- 담당자가 가장 먼저 할 일(선택): 203.0.113.50 이 로그인에 성공한 뒤 요청한 `/admin` · `/admin/users` 가 모두 403(접근 거부)이었는지, 그 뒤에도 요청이 이어졌는지 로그에서 확인합니다.

#### 상황 7 · 정산 조회 시도에는 알림이 나지 않음
- 원인: 규칙 문제. seoyeon의 서버 실패 2건은 반복 기준 3건보다 적어 중요한 정산 조회도 빠진다.
- 고칠 파일: `access_detection.py`. 점수에 반영하려면 `risk_scores.py`의 수집 부분도 연결한다.
- 어떻게 고치나요: `SETTLE:QUERY` 같은 중요 권한을 정하고 권한 없는 접근을 횟수와 관계없이 확인하는 규칙을 추가한다.
- 고친 뒤 확인: P5가 탐지되는지 확인하고 조사 결과와 대조해 오탐·미탐을 다시 센다.
- 담당자가 가장 먼저 할 일(선택): 정산 조회가 승인된 업무였는지와 당시 권한을 확인한다.

#### 상황 8 · 서버가 같은 네트워크에 열려 있고, 지우면 접속 기록도 사라짐
- 원인: 운영 설정 문제. 모든 인터페이스에 포트를 공개하고, 로그를 컨테이너 내부에만 보관했기 때문이다.
- 고칠 파일: `compose.secure.yaml`.
- 어떻게 고치나요: 관리용 web2는 `127.0.0.1:8081:80`으로 제한하고, 로그 보관용 web3는 `./logs:/var/log/nginx`를 연결한다. 현재 보안 설정에는 이미 반영돼 있다.
- 고친 뒤 확인: ps에서 로컬 바인딩을 확인한다. 11/6 실습에서는 down 이후에도 access.log·error.log·web_404.log가 남는 것을 확인했다.
- 담당자가 가장 먼저 할 일(선택): 불필요한 외부 노출을 확인하고 원본 로그를 보존한다.
